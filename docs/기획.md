# 보드 동아리 오늘 현황판 기획

## 1. 한 줄 정의

동아리원이 매일 이름만 확인하고, **오늘 보드를 탈 예정인지**와 **현재 동방/라이딩 중인지**를 한 화면에서 공유하는 모바일 우선 현황판이다.

서비스는 회원가입이나 계정 로그인을 사용하지 않는다. 이름은 동아리 명단과만 대조하며, 상태를 처음 등록할 때 오늘 하루 동안 사용할 입장자 ID를 발급한다.

---

## 2. 제품 목표

- 단톡방 링크 하나로 오늘의 참여 현황을 빠르게 확인한다.
- 처음 접속한 사람도 설명 없이 이름 입력과 버튼 클릭만으로 사용할 수 있어야 한다.
- 같은 날에는 브라우저를 닫았다가 다시 접속해도 이름과 상태가 유지되어야 한다.
- KST 날짜가 바뀌면 전날 입장자와 상태는 모두 무효가 되고 이름 입력부터 다시 시작한다.
- 기능은 단순하게 유지하되, 교실 뒤편의 코르크 핀보드처럼 친근하고 귀여운 인상을 준다.

## 3. 범위 밖

- 회원가입, 개인 계정, 소셜 로그인, PIN
- 상태 변경 이력과 통계
- 출석 관리
- 푸시·카카오톡 알림
- 프로필 사진 업로드와 아바타 꾸미기
- 시간 기반 자동 만료
- 기기 간 상태 동기화

---

## 4. 핵심 개념

### 4.1 명단과 오늘의 입장자

- `roster`는 회장이 관리하는 학기 명단이다.
- 같은 이름을 여러 번 등록할 수 있다. 중복된 각 행을 한 명의 자리로 본다.
- 이름 입력은 명단 확인만 수행하며, 이 시점에는 DB에 입장자를 만들지 않는다.
- 사용자가 상태를 처음 클릭할 때만 오늘의 입장자 `member`를 만든다.
- 입장자는 오늘 KST 날짜에만 유효하다.
- 다음 날에는 같은 사람도 이름을 다시 입력하고, 상태를 처음 누를 때 새 입장자 ID를 받는다.

### 4.2 관전 상태

이름 확인 후 아직 어떤 상태도 등록하지 않은 상태다.

- 현황판과 모든 명단을 볼 수 있다.
- DB에는 입장자나 상태 기록이 없다.
- 다른 사람에게 본인 이름이 표시되지 않는다.

### 4.3 상태 모델

상태는 하나의 열거형이 아니라, 서로 독립적인 두 축으로 관리한다.

```text
탑승 계획
- planned: true / false

현재 위치
- location: null / in_room / riding
```

- `planned`는 현재 위치와 동시에 선택할 수 있다.
- `in_room`과 `riding`은 서로 동시에 선택할 수 없다.
- 위치가 `null`이면 동방도 아니고 보드를 타는 중도 아닌 상태다.
- 위치 `없음` 버튼은 화면에 따로 표시하지 않는다.

가능한 조합은 다음과 같다.

| planned | location | 화면 표시 |
|---|---|---|
| false | null | 어디에도 표시되지 않음(관전) |
| true | null | 오늘 탈 사람 |
| false | in_room | 지금 동방 |
| true | in_room | 오늘 탈 사람 + 지금 동방 |
| false | riding | 지금 타는 중 |
| true | riding | 오늘 탈 사람 + 지금 타는 중 |

## 5. 사용자 흐름

### 5.1 오늘 처음 접속

1. 단톡방 링크로 `/`에 접속한다.
2. 이름을 입력하고 `보드에 붙이기` 버튼을 누른다.
3. 서버가 이름을 명단과 대조한다.
4. 명단에 있으면 현황판을 보여준다.
5. 브라우저가 오늘 등록 요청의 멱등성을 위한 임의의 `clientNonce`를 생성해 저장한다.
6. 아직 상태를 누르지 않았으므로 관전 상태로 시작한다.
7. 첫 상태 클릭 시 서버가 오늘의 입장자 ID를 만들고 상태를 저장한다.

명단에 없는 경우:

```text
명단에 없는 이름이에요. 회장에게 문의해 주세요.
```

### 5.2 같은 날 재접속

- 같은 기기·같은 브라우저라면 이름 입력을 생략하고 현황판을 바로 보여준다.
- 상태를 등록했던 사용자는 기존 상태가 그대로 선택되어 있다.
- 관전만 했던 사용자도 이름 확인 결과는 유지되며, 계속 관전 상태로 들어온다.

### 5.3 날짜 변경

- 날짜 기준은 항상 KST(`Asia/Seoul`)다.
- 오늘 날짜가 localStorage에 저장된 입장 날짜와 다르면 로컬의 이름과 입장자 ID를 무효화한다.
- 이름 입력 화면부터 다시 보여준다.
- 전날 `member_id`로는 상태를 변경할 수 없다.
- 자정에 실제 전체 삭제 작업이나 스케줄러를 실행하지 않는다. 서버는 오늘 날짜의 데이터만 유효하게 취급한다.
- 앱을 자정 넘게 열어 둔 경우, 다음 폴링 응답의 서버 날짜가 바뀌는 즉시 이름 입력 화면으로 전환한다.

### 5.4 이름 변경

- 오늘 아직 입장자 ID가 없다면 로컬 이름만 지우고 이름 입력 화면으로 돌아간다.
- 상태가 등록된 상태에서 이름을 바꾸면, 현재 입장자와 상태를 서버에서 삭제한 뒤 로컬 정보를 지운다.
- 삭제 전 다음 확인 문구를 표시한다.

```text
현재 상태를 모두 지우고 이름을 바꿀까요?
```

## 6. 상태 조작 규칙

### 6.1 상단 버튼

```text
[ 오늘 보드 탈 예정 ]

[ 동방에 있음 ] [ 보드 타는 중 ]
```

- `오늘 보드 탈 예정`은 독립 토글이다.
  - 꺼진 상태에서 클릭: `planned = true`
  - 켜진 상태에서 재클릭: `planned = false`
- `동방에 있음`을 클릭하면 `location = in_room`이 된다.
- 선택된 `동방에 있음`을 다시 클릭하면 `location = null`이 된다.
- `보드 타는 중`을 클릭하면 `location = riding`이 된다.
- 선택된 `보드 타는 중`을 다시 클릭하면 `location = null`이 된다.
- `동방에 있음`과 `보드 타는 중` 사이를 누르면 즉시 해당 위치로 전환된다.
- 위치 변경은 `planned` 값을 변경하지 않는다.
- 선택된 버튼은 색상, 눌린 깊이, 아이콘으로 활성 상태를 명확히 표시한다.

### 6.2 본인 이름 스티커의 `×`

- 본인의 이름 스티커에만 `×`를 표시한다.
- `오늘 탈 사람`에서 `×` 클릭: `planned = false`
- `지금 동방` 또는 `지금 타는 중`에서 `×` 클릭: `location = null`
- 다른 사람의 이름 스티커는 클릭할 수 없다.
- 전체 상태 제거 버튼은 두지 않는다. 각각의 버튼 또는 본인 스티커의 `×`로 해제한다.

### 6.3 저장과 갱신

- 상태 버튼을 누르면 중복 클릭을 잠시 막고 서버 응답 후 UI를 확정한다.
- 상태 변경 성공 직후 현황판을 다시 조회한다.
- 그 외에는 10초마다 자동 갱신한다.
- 오래된 폴링 응답이 최신 상태 변경 결과를 덮어쓰지 않도록 요청 순서를 관리한다.
- 요청 실패 시 이전 선택 상태로 되돌리고 짧은 오류 메시지와 재시도 수단을 제공한다.

## 7. 화면 구성

기능 화면은 사용자용 한 화면(`/`)과 관리자 화면(`/admin`)으로 구성한다. 별도 `/board` 라우트는 사용하지 않는다.

### 7.1 사용자 화면 (`/`)

#### 이름 입력 상태

- 코르크 보드 위에 핀으로 고정된 종이 형태의 입력 카드
- 문구: `새 스티커에 이름을 써주세요`
- 이름 입력 필드
- `보드에 붙이기` 버튼
- 공백 이름은 허용하지 않는다.
- 이름 앞뒤 공백은 제거한다.
- 이름은 명단과 대소문자를 포함해 정확히 비교한다.

#### 현황판 상태

상단부터 다음 순서로 배치한다.

1. 서비스 제목과 KST 오늘 날짜
2. `○○○의 오늘` 상태 조작 메모지
3. `오늘 탈 사람` 메모지
4. `지금 동방` 메모지
5. `지금 타는 중` 메모지
6. 이름 변경 링크와 관리자 진입 링크

각 명단 메모지는 다음 정보를 포함한다.

- 섹션 아이콘과 제목
- 현재 인원 수
- 이름 스티커 목록
- 비어 있을 때의 안내 문구

빈 상태 문구 예시:

| 섹션 | 문구 |
|---|---|
| 오늘 탈 사람 | 아직 탈 예정인 사람이 없어요 ⭐ |
| 지금 동방 | 동방이 아직 조용해요 🫧 |
| 지금 타는 중 | 아직 보드를 타는 사람이 없어요 🛹 |

### 7.2 이름 스티커

- 프로필 사진 대신 색상, 작은 장식 아이콘, 이름으로 구성한다.
- 색상과 장식은 입장자 ID에서 결정적으로 생성하여 새로고침해도 유지한다.
- 동명이인은 서로 다른 입장자 ID를 가지므로 다른 색상·장식으로 구분된다.
- 본인 스티커는 더 진한 외곽선 또는 작은 `나` 표시를 추가한다.
- 본인 스티커에만 충분한 크기의 `×` 터치 영역을 제공한다.
- 상태 등록 시 스티커가 붙는 짧은 애니메이션을 사용한다.
- 상태 해제 시 스티커가 살짝 들리며 사라지는 애니메이션을 사용한다.
- `prefers-reduced-motion` 환경에서는 애니메이션을 제거한다.

### 7.3 비주얼 콘셉트

**교실 뒤편의 알록달록한 코르크 핀보드**를 기본 콘셉트로 한다.

- 전체 배경: 과하지 않은 따뜻한 코르크 질감
- 상태 영역: 핀으로 고정한 노랑·민트·하늘색 종이
- 사람 표시: 다이컷 이름 스티커
- 장식: 압정, 마스킹 테이프, 별, 번개, 꽃, 체커보드, 작은 보드 낙서
- 글자는 질감과 분리된 깨끗한 종이 위에 배치해 가독성을 확보한다.
- 색상만으로 상태를 구분하지 않고 텍스트와 아이콘을 함께 사용한다.
- 장식은 클릭 가능한 요소처럼 보이지 않게 한다.

### 7.4 반응형과 접근성

- 모바일을 기본으로 메모지 세 장을 세로로 배치한다.
- 넓은 화면에서는 세 상태 메모지를 가로 3열로 배치할 수 있다.
- 모든 버튼과 `×`의 터치 영역은 최소 44×44px을 확보한다.
- 키보드 포커스와 스크린 리더용 레이블을 제공한다.
- 본문과 버튼은 코르크 배경 위에서도 충분한 명도 대비를 유지한다.
- 상태 변경 결과와 오류는 텍스트로도 전달한다.

### 7.5 관리자 화면 (`/admin`)

- 관리자 비밀번호 입력 후 진입
- 비밀번호는 현재 탭의 `sessionStorage`에서만 유지하고 영구 저장하지 않는다.
- 명단 목록과 전체 인원 수
- 이름 한 명 추가
- 줄바꿈으로 구분한 여러 이름 일괄 추가. 한 줄에 `학번 이름`을 입력하면 같은 학번은 한 번만 등록하고, 학번은 관리자 화면에서만 표시한다.
- 명단 한 자리 삭제
- 오늘의 입장자 목록
- 이름별 `오늘 입장자 수 / 명단 자리 수` 표시
- 오늘의 입장자 한 명 삭제
- 명단과 모든 입장자 전체 초기화
- 파괴적인 작업에는 대상과 결과가 드러나는 확인 문구 사용
- 관리자 화면은 기능 우선으로 구성하되 사용자 화면과 동일한 색상·종이 요소를 일부 사용한다.

## 8. 로컬 저장 모델

localStorage에는 오늘의 입장 상태만 저장한다.

```json
{
  "name": "김민서",
  "day": "2026-10-14",
  "clientNonce": "random-uuid",
  "memberId": "uuid-or-null"
}
```

- 키 예시: `obt.daily-entry.v1`
- 이름 확인 직후 `name`, `day`, 새로 생성한 `clientNonce`를 저장한다.
- 첫 상태 클릭으로 등록에 성공하면 `memberId`를 추가한다.
- 동일한 `clientNonce`로 `register`가 재호출되면 기존 결과를 반환하여 이중 클릭이나 응답 유실로 같은 사람이 자리를 두 개 차지하지 않게 한다.
- `memberId`는 서버의 `get_board()` 결과에 공개하지 않는다.
- 저장된 날짜가 서버의 오늘 날짜와 다르면 전체 값을 삭제한다.
- 저장값이 손상됐거나 서버에서 해당 입장자를 찾지 못하면 `memberId`만 제거하고 필요 시 다시 등록한다.

## 9. 데이터 모델 (Supabase Postgres)

### 9.1 테이블

```text
roster
  id          uuid  PK default gen_random_uuid()
  name        text  NOT NULL CHECK (char_length(name) BETWEEN 1 AND 30)
  student_id  text  NULL CHECK (student_id ~ '^[0-9]{5,20}$')
                              -- 관리자 화면 전용. 같은 사람의 중복 등록 방지용
  created_at  timestamptz NOT NULL default now()
  UNIQUE (student_id)         -- 학번이 있는 행만 (partial unique index)

members                         -- 상태를 처음 누를 때 생성되는 날짜별 입장자
  id          uuid  PK default gen_random_uuid()
  roster_id   uuid  NOT NULL FK -> roster.id ON DELETE CASCADE
  name        text  NOT NULL CHECK (char_length(name) BETWEEN 1 AND 30)
                              -- 표시용 이름 스냅샷
  day         date  NOT NULL    -- KST 입장 날짜
  client_nonce uuid NOT NULL    -- 같은 브라우저의 등록 재시도 식별자
  created_at  timestamptz NOT NULL default now()
  UNIQUE (roster_id, day)
  UNIQUE (day, client_nonce)

statuses
  member_id   uuid  PK FK -> members.id ON DELETE CASCADE
  planned     boolean NOT NULL default false
  location    text NULL CHECK (location IN ('in_room', 'riding'))
  updated_at  timestamptz NOT NULL default now()

app_settings
  key         text  PK
  value       text  NOT NULL
```

`app_settings`에는 `admin_password_hash`를 저장한다.

### 9.2 모델 결정 이유

- `members.day`로 날짜별 입장자를 분리한다.
- `roster_id + day` 유니크 제약으로 명단 한 자리당 하루에 한 입장자만 배정한다.
- `day + client_nonce` 유니크 제약으로 같은 브라우저의 등록 재시도를 멱등 처리한다.
- 중복 이름은 서로 다른 `roster_id`를 가지므로 각각 입장할 수 있다.
- 명단 한 자리를 삭제하면 그 자리에 연결된 입장자와 상태도 함께 삭제된다.
- 입장자가 날짜별이므로 `statuses`에는 별도 날짜 열이 필요하지 않다.
- `planned`와 `location`을 분리하여 상태 규칙을 DB 구조 자체에 반영한다.

### 9.3 날짜와 정리 정책

- 서버 날짜는 `(now() AT TIME ZONE 'Asia/Seoul')::date`로 계산한다.
- 모든 사용자 RPC는 서버 날짜를 기준으로 검증한다.
- 오늘이 아닌 `members`와 연결 상태는 조회 및 변경 대상에서 제외한다.
- 정확한 자정 삭제 작업은 실행하지 않는다.
- 오래된 입장자는 필요할 때 수동 또는 선택적 정리 함수로 삭제한다.
- 동아리 규모에서는 누적량이 작지만, 운영 편의를 위해 30~90일 이전 행 삭제를 추후 추가할 수 있다.

## 10. API (Postgres RPC, `SECURITY DEFINER`)

테이블 직접 접근은 RLS로 막고, 필요한 함수만 `anon` 역할에 실행 권한을 부여한다.

| 함수 | 입력 | 반환/동작 |
|---|---|---|
| `check_name(p_name)` | 이름 | 정규화된 이름이 명단에 있는지와 서버의 오늘 날짜 반환 |
| `get_board(p_member_id default null)` | 선택적 본인 ID | 서버 날짜, 세 명단, 인원 수, 각 항목의 이름·스티커 시드·`is_me`, 본인 현재 상태 반환 |
| `register(p_name, p_client_nonce)` | 이름, 브라우저가 생성한 임의 UUID | 오늘의 명단 빈자리를 원자적으로 배정하고 입장자 ID 반환. 같은 요청 재시도는 기존 결과 반환 |
| `set_planned(p_member_id, p_on)` | 입장자 ID, 목표값 | 오늘 입장자인지 검증 후 `planned`를 정확한 목표값으로 저장 |
| `set_location(p_member_id, p_location)` | 입장자 ID, `in_room`/`riding`/null | 오늘 입장자인지 검증 후 위치를 정확한 목표값으로 저장 |
| `leave_today(p_member_id)` | 입장자 ID | 오늘의 본인 입장자와 상태 삭제. 이름 변경에 사용 |
| `admin_list(p_pw)` | 비밀번호 | 명단, 오늘 입장자, 이름별 자리 현황 반환 |
| `admin_add(p_pw, p_entries)` | 비밀번호, `[{name, student_id}]` | 이름이 빈 항목을 제외하고 명단에 일괄 추가. 이미 등록된 학번은 건너뛰고, 학번이 다르거나 없는 같은 이름은 동명이인 자리로 추가. `{added, skipped}` 반환 |
| `admin_remove(p_pw, p_roster_id)` | 비밀번호, 명단 자리 ID | 명단 한 자리와 연결된 입장자·상태 삭제 |
| `admin_remove_member(p_pw, p_member_id)` | 비밀번호, 입장자 ID | 오늘의 입장자와 상태 삭제 |
| `admin_reset(p_pw)` | 비밀번호 | 명단과 모든 입장자·상태 전체 삭제 |

### 10.1 `register` 세부 규칙

1. 이름 앞뒤 공백을 제거하고 빈 이름을 거부한다.
2. 같은 날짜와 `clientNonce`로 생성된 입장자가 있으면 이름이 일치하는지 확인하고 기존 ID를 반환한다.
3. 같은 이름의 명단 자리와 오늘 배정된 자리를 이름 단위 잠금 안에서 확인한다.
4. 빈 명단 자리가 있으면 한 자리를 배정해 오늘의 입장자를 만든다.
5. 명단 자리가 한 개뿐이고 이미 오늘 입장자가 있다면 기존 입장자 ID를 반환한다.
6. 같은 이름의 명단 자리가 여러 개이며 모두 찼다면 동명이인을 구분할 수 없으므로 등록을 거부한다.
7. 동시에 여러 요청이 들어와도 명단 수보다 많은 입장자가 생성되지 않아야 한다.

이름 단위 advisory lock 또는 잠긴 명단 행 선택과 유니크 제약을 함께 사용한다.

### 10.2 `get_board` 공개 정보

- URL을 아는 누구나 오늘 활성 상태와 이름을 조회할 수 있다.
- 실제 `member_id`는 응답 목록에 포함하지 않는다.
- `clientNonce`도 어떤 공개 응답에도 포함하지 않는다.
- `p_member_id`를 전달한 경우 서버가 각 항목에 `is_me`만 계산해 반환한다.
- 스티커 색상·장식 생성을 위한 공개용 안정적 시드가 필요하면 실제 ID 대신 별도 파생값을 반환한다.
- 상태가 모두 꺼진 입장자는 명단에 반환하지 않는다.

### 10.3 오류 코드

프론트가 문자열 문구에 의존하지 않도록 RPC는 구분 가능한 오류 코드를 제공한다.

| 코드 | 의미 | 프론트 동작 |
|---|---|---|
| `NAME_NOT_FOUND` | 명단에 없는 이름 | 이름 입력 화면에 안내 |
| `NAME_SLOTS_FULL` | 동명이인 자리가 모두 사용 중 | 회장에게 입장자 정리를 요청하도록 안내 |
| `MEMBER_NOT_FOUND` | 삭제되거나 잘못된 입장자 ID | 로컬 ID 제거 후 등록을 한 번 재시도 |
| `MEMBER_EXPIRED` | 전날 입장자 ID | 로컬 입장 정보 전체 제거 후 이름 입력 화면 표시 |
| `INVALID_STATUS` | 허용하지 않은 상태값 | 이전 UI 상태 복원 |
| `ADMIN_UNAUTHORIZED` | 관리자 비밀번호 불일치 | 관리자 로그인 오류 표시 |

## 11. 동명이인 정책

예를 들어 명단에 `김민서`가 두 줄 있으면 오늘 `김민서` 입장자도 최대 두 명까지 만들 수 있다.

- 각 명단 행은 별도의 `roster_id`를 가진다.
- 각 입장자는 별도의 ID와 스티커 모양을 가진다.
- 두 명 모두 활성 상태라면 명단에 `김민서`, `김민서`가 각각 표시된다.
- 같은 이름의 마지막 빈자리는 먼저 상태를 등록한 요청이 사용한다.
- 브라우저 데이터가 지워져 자리가 찬 경우 관리자가 오늘 입장자를 삭제해 자리를 비운다.
- 명단이 한 자리뿐인 이름은 재등록 시 기존 오늘 입장자 ID를 반환해 복구를 돕는다.

## 12. 보안과 의도적 한계

### 12.1 필수 방어

- 모든 테이블에 RLS를 활성화한다.
- `anon`, `authenticated`의 테이블 직접 권한을 제거한다.
- 필요한 RPC에만 `EXECUTE` 권한을 부여한다.
- 모든 `SECURITY DEFINER` 함수에 고정된 `search_path`를 지정한다.
- 함수 내부에서 테이블과 함수 스키마를 명시한다.
- 관리자 비밀번호는 `pgcrypto`의 bcrypt 방식으로 해시해 저장하고 `crypt()`로 비교한다.
- 관리자 설정이 없거나 빈 비밀번호가 들어오면 항상 실패한다.
- 실제 입장자 ID는 공개 현황판 결과에 노출하지 않는다.

### 12.2 수용하는 한계

- 이름만 아는 사람이 타인의 이름으로 입장할 수 있다.
- 명단이 한 자리뿐인 이름은 같은 이름을 입력해 기존 오늘 입장자 ID를 다시 받을 수 있다.
- URL을 아는 누구나 오늘 현황과 전체 이름을 볼 수 있다.
- 관리자 비밀번호 RPC에 별도 계정 기반 로그인이나 정교한 요청 제한은 없다.
- localStorage 값을 삭제하거나 다른 브라우저를 사용하면 새 기기로 취급한다.

이 서비스는 동아리 내부용 최소 울타리를 목표로 하며 강한 본인 인증은 제공하지 않는다.

## 13. 기술 스택과 무료 운영

- 프론트엔드: Vite + React + TypeScript
- 스타일: CSS 또는 가벼운 스타일 계층. 코르크·종이·스티커는 가능한 한 CSS로 표현
- 백엔드: Supabase Postgres + RPC
- 데이터 갱신: 10초 폴링, 상태 변경 직후 즉시 재조회
- 배포: Vercel 또는 Cloudflare Pages의 무료 정적 배포
- 별도 서버, 자정 스케줄러, Realtime 구독은 사용하지 않음
- 환경변수: Supabase URL과 anon key만 프론트에 제공하며 service role key는 절대 포함하지 않음

## 14. 수용 기준

### 입장과 날짜

- 명단에 있는 이름만 오늘 화면에 입장할 수 있다.
- 이름 확인만 하고 관전하면 DB에 입장자가 생기지 않는다.
- 첫 상태 클릭 시 한 번만 오늘 입장자가 생성된다.
- 같은 날 재접속하면 이름 입력을 생략하고 상태가 유지된다.
- KST 날짜가 바뀌면 이름 입력부터 다시 시작한다.
- 전날 입장자 ID로 상태를 변경할 수 없다.

### 상태

- 예정과 동방을 동시에 선택할 수 있다.
- 예정과 타는 중을 동시에 선택할 수 있다.
- 동방과 타는 중은 동시에 선택할 수 없다.
- 활성 버튼을 다시 누르면 해당 상태만 해제된다.
- 본인 이름의 `×`로 동일한 상태를 해제할 수 있다.
- 다른 사람 이름에는 `×`가 보이지 않고 조작할 수 없다.

### 동명이인과 동시성

- 명단 중복 수만큼 같은 이름의 오늘 입장자를 만들 수 있다.
- 같은 이름이 동시에 등록되어도 명단 자리 수를 초과하지 않는다.
- 같은 브라우저의 등록 요청이 재시도되어도 입장자는 한 명만 생성된다.
- 동명이인은 현황판에 각각 표시되고 스티커 모양으로 구분된다.

### 관리자

- 비밀번호 없이는 명단과 입장자 목록을 조회·변경할 수 없다.
- 명단을 한 자리 삭제하면 연결된 오늘 입장자와 상태도 삭제된다.
- 오늘 입장자 삭제 후 해당 명단 자리에 다시 등록할 수 있다.
- 전체 초기화는 명단, 입장자, 상태를 모두 삭제한다.

### UI

- 360px 너비 모바일 화면에서 가로 스크롤 없이 사용할 수 있다.
- 버튼과 `×`가 터치하기 충분한 크기다.
- 빈 명단, 로딩, 네트워크 오류, 등록 거부 상태가 각각 구분된다.
- 색상 없이도 텍스트와 아이콘으로 상태를 이해할 수 있다.
